## Decisions

1. **The snapshot is the CONTRACTS §4.5 revision 3 shape**: one sample's columns plus `cpuCores`,
   `memUsedMiB`, `diskTotalMiB` and a GPU list. `gpu` has three states — absent (not known), `null`
   (asked, no GPU), a list — so "No GPU" (S2) and "—" for an unreadable GPU (U8) are both honest. FR-2's
   "absent when no GPU" is read as "no GPU object".
2. **Drop, never clamp.** `sanitizeFleetNodeHealthSnapshot` runs at both ends and drops any value outside
   its bounds; a clamped 100% would be a number the machine never reported (FR-4, FR-30). The heartbeat
   DTO is only `@IsObject()` (like `workerState` is not an `@IsIn`): a value this build rejects must never
   400 the beat, because a 400 is a node swept offline. T-06's "out-of-range refused" is therefore "refused
   by the sanitiser, field dropped", never the request.
3. **`health` rides its own newest heartbeat tier**, so a platform older than the field costs exactly that
   field (FR-3, U9). Enrolment never carries it (enrolment has no strip-and-retry). The tier-drop warning
   became tier-aware so each latch names what it dropped.
4. **CPU and memory come from the admission gate's own sampler** (`createResourceProbe`), in a separate
   instance (a shared one would split each delta with the gate) with an opt-in 250 ms first-sample window,
   so the first beat's CPU is a real reading rather than the gate's "0% admits work" bias.
5. **Per-OS facts.** Linux: failed systemd units; pending reboot from `/var/run/reboot-required`, else
   `false` on the Debian family, else `needs-restarting -r`. Windows: one PowerShell start (sent with
   `-EncodedCommand`, because the node's runner spawns through `cmd.exe`, which would split a pipeline)
   answers the two servicing/Windows Update reboot keys, automatic services stopped with a failure exit
   code (excluding 1077, "never started since boot"), and the display adapters; load average is dropped on
   Windows (it always reads 0). macOS: neither pending reboot nor failed services — not honestly knowable
   cheaply (`launchctl` non-zero exits are normal noise). GPU: `nvidia-smi` on every OS (fresh every beat),
   `rocm-smi` for AMD on Linux, `ioreg` utilisation for Apple.
6. **Slow facts run off the beat**: pending reboot, failed services and GPU identity are cached (5 min /
   10 min) and refreshed with a 15 s deadline. The first read waits at most the beat's 2 s budget (a long
   first probe lands on a later beat); at expiry the beat is served the answer in hand while ONE refresh
   runs in the background (`refreshInBackground`; review finding), so a slow tool never blinks a fact to
   "—". A refresh's "could not ask" still replaces the value. Every fact is its own probe; nothing can fail
   or delay the beat. Pending reboot from `needs-restarting -r` is "yes" only on exit 1 with its own
   "Reboot is required" sentence and no spawn error: the runner reports a missing tool as exit 1 too.
7. **State precedence** (`resolveComputerState`): enrolling → offline → quarantined (the machine's own
   fault outranks the owner's pause/drain) → draining/disabled → paused → upgrade-required → throttled
   (resource, proven from the reported numbers) / limited (model CLI) → busy → online. `limited` only when
   the node reports `throttled` or every model CLI it advertises is out of quota — a node with one CLI
   still usable is busy/online, not "waiting". Agreement with the footer runner pill is pinned by a web test
   that imports the real `runnerRowState`.
   Owner default (spec §8b): the words "Limited" and "Throttled", both the one `node-throttled` kind.
8. **Two platform markers live in the stored snapshot**: `diskLowSince` (a stable `since` for the
   `disk-low` item, FR-17) and `sampledAt` (the 55 s history floor read back from the row, so FR-18 holds
   across API replicas — a node may beat every 5 s and an in-process memory would let every replica write).
9. **History**: one table, `resolution: raw | hourly`, hourly rows carry means plus `cpuMax`/`memMax`/
   `diskMax` (CONTRACTS rev 3). The roll-up is portable (hours bucketed in code from indexed reads,
   insert-or-ignore on the unique key → a re-run is a no-op), rolls only hours that ended ≥ 5 min ago,
   oldest first, ≤ 48 per pass, never the hour the 7-day cutoff cuts through, and prunes after rolling. It
   runs as the `fleet-health-rollup` Trigger.dev cron; the API runs the same pass in-process only when
   Trigger.dev is not the runtime (the `SkillReadinessSweepCronService` fallback shape). The writer and the
   roll-up are in P1 (the plan had them in P2) because the lane brief puts the samples table, writer and
   roll-up in P1; the history endpoint and chart stay in P2.
10. **Producers**: `disk-low` skips offline computers (their numbers may be hours old); `consent-missing`
    and `helper-untrusted` fire only on REPORTED fields, never on an absent one. Items are FL-01's exact
    §4.6 shape: an English `title` and `detail` read as is by the hub, Agents, MCP and the CLI (no
    per-item message keys — owner question 6). An action navigates or runs the one named command; a machine
    command the platform cannot run (clear quarantine, start with a consent) is written in `detail` and
    the action opens the computer page, where it has a copy button. Every item survives FL-01's
    `normalizeNeedsALookItem` unchanged (tested through the real registry).
11. **Clear limit now** keeps the existing owner-only check, which IS the `machines` default audience
    (CONTRACTS §2.1). Widening it to Organization roles is FL-01's role derivation; nothing changed here.
12. **Refresh now** is shown disabled with its reason until PR 2 brings the link request (R-31).
13. **Reset times** show in the viewer's zone with UTC in the tooltip (FR-11); the machine's own zone waits
    for FL-13's `timeZone`.
14. **Health is on the shared view.** FL-01's allow-list makes a new shared field a decision; FL-03's spec
    §7 makes it ("Read health / history: `view` / org-members"). The snapshot is numbers, booleans, a
    failed-service count and bounded GPU names; the disk floor and the resource ceilings stay withheld, so a
    shared reader's disk-low is the percentage rule only. `GET /nodes/:id/health` reads through FL-01's
    `getVisibleForUser` and composes the job count only for the owner (the jobs are the owner's ledger).
15. **Silence is offline.** `resolveComputerState` takes `offlineAfterMs`: a computer whose last beat is
    older than `FLEET_NODE_OFFLINE_AFTER_MS` reads `offline` whatever its stored status says, because the
    sweep runs only on the owner's list read and flips only `online` rows. The health read and every
    producer pass it (review finding), so a machine silent for an hour is never "online", "quarantined" or
    "disk low" from its last report.
16. **A disk-low marker without a snapshot.** A daemon older than the snapshot still reports free disk and
    its floor; its row stores `{ at, diskLowSince }` while the floor rule says low, cleared on recovery,
    so its `disk-low` item keeps one `since` (review finding). `hasFleetNodeHealthReading` tells this
    marker from a reading; the API answers it as "no snapshot", the web shows "this version reports no
    health", and nothing is sampled from it.
17. **"Change limits" opens Settings → Fleet**, where `PUT /nodes/:id/limits` lives today; the computer
    page's Settings tab is FL-01's and still a placeholder. One route for the block and the producers.
18. **Column types**: `macAddress` and `lanId` are `text` (CONTRACTS §4.1; review finding — they were
    varchar 17 / 16). `lastWakeAttemptAt` is the repo's `PortableDateColumn` (`timestamp`, as every
    portable date column), where §4.1 writes `timestamptz`; the entity and the migration agree.
19. **Roll-up failure is loud, retention still runs.** A roll-up that throws still prunes (raw stays
    bounded), then fails the run. The hourly insert goes 500 rows a statement (parameter caps).
20. **The probe stops when the platform strips `health`** (`HeartbeatLoop.isDropping`), instead of
    spawning its tools every beat for a field that is thrown away.

## Questions for the owner

1. **Spec S5's example contradicts FR-12.** "At 9 GiB free and 88% full it is `warn`" — 88% full is 12% free,
   which FR-12's "below 10% of the volume" does not catch. Implemented FR-12 (the normative text). Should the
   warning threshold be 15% (or "≥ 85% full") instead?
2. **The existing Windows GPU capability probe never works for a non-NVIDIA card.** `gpuProbesFor('win32')`
   runs `powershell -Command "Get-CimInstance … | Select-Object …"` through a runner that spawns via
   `cmd.exe`, which splits the pipeline (verified on this machine: exit 255). Such a machine never advertises
   `gpu`. The health probe uses `-EncodedCommand` and is unaffected; fixing the capability probe would start
   advertising `gpu` / `gpu:<vendor>` on those machines and so change job routing — left as is, pending a yes.
3. **macOS reports no pending reboot or failed services.** Acceptable, or should a best-effort (e.g.
   `softwareupdate` restart-required) be added?
4. **`consent-missing` offers `ever-works-node start --work`** as its one command (the sentence names all three
   consents). Prefer a different default?
5. **History backlog**: an hour older than the 7-day raw window that was never rolled up (Trigger.dev down for
   a week) is lost for the 7 d / 90 d views. Acceptable?
6. **"Needs a look" items are English only.** FL-01's §4.6 item has no message key, so FL-03's sentences are
   English for every viewer (the state words and sentences on the computer page ARE localised). Should §4.6
   gain an optional `messageKey` + `params` so the hub can localise items? FL-03's producers already build
   every sentence from named parts, so it is a small change either way.
7. **macOS memory reads high.** The node's admission sampler (reused, as the brief asks) uses `os.freemem()`,
   which on macOS counts only free pages, not inactive or purgeable ones — "Memory 9x%" on a healthy Mac.
   The admission gate has always judged by this number; publishing it makes it visible. Fixing it (e.g.
   `vm_stat`) changes when a Mac admits work. Fix in FL-03 P2, or leave the gate's number?
8. **A hung tool is not reaped on Windows.** The node's command runner spawns through `cmd.exe` on Windows
   (`shell: true`), so its timeout kills the shell, not `powershell` or `nvidia-smi`. Existing exposure
   (the capability probes do the same); the health probe adds a spawn per beat. Changing the shared runner
   affects every probe — do it in its own change?
9. **Shared readers and the disk floor.** Org members see disk-low only by the percentage rule (decision
   14). Should the floor (a limit the owner set) be shared so they also see "the node stops at 5 GiB"?
